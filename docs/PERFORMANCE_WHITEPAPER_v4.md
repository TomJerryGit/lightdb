## 1. 摘要

### 1.1 核心结论

v4.0 相比 v3.0：

| 指标         | v3.0     | v4.0       | 提升      |
|--------------|:--------:|:----------:|:---------:|
| 单线程点查   | 6,500 QPS| 12,000 QPS | +85%      |
| 8 核点查     | 8,200 QPS| 92,000 QPS | +1022%    |
| 并发 TPS     | -        | 22,000 TPS | 新增      |
| 批量插入     | 70K/s    | 150K/s     | +114%     |
| OLAP 扫描    | 不支持   | 3.5M rows/s| 新增      |
| 大表聚合     | 不支持   | 85M rows/s | 新增      |

v4.0 相比 MySQL 5.7：

| 场景         | LightDB v4  | MySQL 5.7   | 达成      |
|--------------|:-----------:|:-----------:|:---------:|
| 单线程点查   | 12,000      | 8,000       | 150%      |
| 8 核点查     | 92,000      | 28,000      | 328%      |
| 并发 TPS     | 22,000      | 5,500       | 400%      |
| OLAP 扫描    | 3.5M rows/s | 200K rows/s | 1750%     |
| 大表聚合     | 85M rows/s  | 500K rows/s | 17000%    |

**综合评分**：v4.0 达 MySQL 5.7 的 **125%**。

### 1.2 关键突破

v4.0 的三大突破：

1. **突破 GIL**：多进程 + 共享内存，8 核利用率从 13% 提升到 95%
2. **突破单核瓶颈**：Cython 加速热点，B+Tree 提速 12.5x
3. **新增 OLAP**：列存 + 向量化，聚合性能提升 41x

## 4. 多核并发性能

### 4.1 扩展曲线

8 核机器上测不同并发：

| 线程数 | v3.0 QPS | v4.0 QPS | v4 加速比 |
|:------:|:--------:|:--------:|:---------:|
| 1      | 6,500    | 12,000   | 1.85x     |
| 2      | 6,800    | 23,500   | 1.96x     |
| 4      | 7,200    | 45,000   | 3.75x     |
| 8      | 8,200    | 92,000   | 7.67x     |
| 16     | 8,500    | 95,000   | 7.92x     |

**关键观察**：

- v3.0 从 1 核到 8 核只有 1.26x 提升（GIL 限制）
- v4.0 从 1 核到 8 核有 7.67x 提升（接近线性）
- v4.0 的 8 核利用率：95%

### 4.2 GIL 影响量化

**实验方法**：在 8 核机器上跑 CPU 密集任务

| 并行度 | 多线程加速 | 多进程加速 |
|:------:|:----------:|:----------:|
| 1      | 1.00x      | 1.00x      |
| 2      | 1.02x      | 1.94x      |
| 4      | 1.05x      | 3.82x      |
| 8      | 1.08x      | 7.61x      |

**结论**：

- 多线程加速比永远接近 1，GIL 是硬限制
- 多进程加速接近线性，v4.0 选对了方向

### 4.3 并发 TPS

OLTP 混合负载（90% 读 + 10% 写）：

| 版本 | TPS      | P50 (ms) | P95 (ms) | P99 (ms) |

### 5.2 聚合性能

**测试**：`SELECT SUM(amount) FROM orders`

1000 万行数据：

| 实现                    | 耗时    | 吞吐        |
|-------------------------|:-------:|:-----------:|
| MySQL 5.7（InnoDB）     | 20s     | 500K rows/s |

| v4.0（NumPy 向量化）    | 0.29s   | 34M rows/s  |

### 5.3 分组聚合

**测试**：`SELECT region, SUM(amount) FROM orders GROUP BY region`

1000 万行数据，10 个 region：

| 实现                    | 耗时    | 吞吐        |
|-------------------------|:-------:|:-----------:|
| MySQL 5.7               | 25s     | 400K rows/s |
| v4.0（NumPy + 并行）    | 0.118s  | 85M rows/s  |

**对比 MySQL 加速比**：212x

### 5.4 列裁剪效果

**测试**：只查 3 列 vs 全表 30 列

| 查询范围       | 耗时     | 加速比  |
|----------------|:--------:|:-------:|
| 全表 30 列     | 2.1s     | 1x      |
| 只查 3 列      | 0.22s    | 9.5x    |

**结论**：列存的核心优势是"只读需要的列"。

### 5.5 编码效果

**测试**：1000 万行数据的存储和查询

| 编码    | 存储大小 | 压缩比 | 查询耗时 |
|---------|:--------:|:------:|:--------:|
| Plain   | 80 MB    | 1x     | 0.5s     |
| Dict    | 12 MB    | 6.7x   | 0.4s     |
| RLE     | 3.2 MB   | 25x    | 0.38s    |
| Delta   | 20 MB    | 4x     | 0.42s    |
| BitPack | 15 MB    | 5.3x   | 0.41s    |

**结论**：RLE 压缩比最高，但查询性能差异不大（因为都是解压后计算）。

## 8. 性能优化技术

### 8.1 单核优化

**Cython 加速**：

| 模块              | Python  | Cython  | 加速比  |
|-------------------|:-------:|:-------:|:-------:|
| B+Tree 查询       | 100ms   | 8ms     | 12.5x   |
| 行编码            | 18.3ms  | 6.2ms   | 2.95x   |
| 行解码            | 12.6ms  | 3.1ms   | 4.06x   |
| 谓词过滤          | 15.3ms  | 5.8ms   | 2.64x   |

**二进制行格式**：

| 格式     | 编码    | 解码    | 大小     |
|----------|:-------:|:-------:|:--------:|
| JSON     | 15ms    | 18ms    | 350KB    |
| Binary   | 5ms     | 4ms     | 120KB    |
| 加速     | 3x      | 4.5x    | 2.9x     |

**页预读**：

- 检测顺序访问模式
- 达到阈值后预读后续页
- 提升范围扫描 20%

### 8.2 多核优化

**SO_REUSEPORT**：

- 多个 Worker 独立监听同一端口
- 内核按 hash 分配连接
- 无用户态负载均衡开销

**共享内存**：

- 事务 ID 集中分配
- 缓冲池只读共享
- 统计集中汇总

**工作窃取**：

- 每个 Worker 维护本地任务队列
- 空闲 Worker 从其他 Worker 窃取任务
- 负载均衡，避免长任务拖累

### 8.3 OLAP 优化

**列式存储**：

- 每列独立存储
- 只读需要的列
- 支持 5 种编码

**向量化执行**：

- 每次处理 4096 行
- NumPy 数组运算
- 避免 Python 逐行开销

**并行聚合**：

- 分片并行扫描
- 局部聚合后合并
- COUNT/SUM/AVG 均支持

### 8.4 事务优化

**WAL 批量刷盘**：

- 多事务合并 fsync
- 减少磁盘 IO

**MVCC 快照隔离**：

- 读操作无锁
- 通过 undo log 回溯版本

**锁粒度控制**：

- 行级锁（默认）
- 表级意向锁
- 三色 DFS 死锁检测

## 9. 瓶颈分析

### 9.1 当前瓶颈

通过 `lightdb-diagnose` 分析 v4.0 的瓶颈：

| 模块       | 耗时占比 | 状态           |
|------------|:--------:|----------------|
| B+Tree     | 12%      | 已优化（Cython）|
| 行编解码   | 10%      | 已优化（Cython）|
| 页操作     | 8%       | 已优化          |
| SQL 解析   | 15%      | 待优化（正则）  |
| 计划优化   | 8%       | 一般            |
| 执行器     | 12%      | 一般            |
| 网络       | 18%      | Python socket  |
| GIL 剩余   | 10%      | 部分模块        |
| 其他       | 7%       | -              |

### 9.2 主要瓶颈

**SQL 解析器（15%）**：

- 使用正则表达式实现
- 复杂 SQL 解析慢
- 计划缓存可缓解

**网络层（18%）**：

- Python socket 性能低于 C
- 建议：改用 Cython 或异步 IO

**执行器（12%）**：

- 火山模型（逐行迭代）
- 建议：向量化执行（部分已实现）

### 9.3 未来优化方向

| 优先级 | 方向                | 预期收益 |
|:------:|---------------------|:--------:|
| 高     | 网络层 Cython 化    | 10-20%   |
| 高     | SQL 解析器优化      | 5-10%    |
| 中     | 执行器向量化        | 15-25%   |
| 中     | 计划缓存改进        | 5%       |
| 低     | 存储引擎进一步优化  | 5%       |

### 9.4 长期瓶颈

**Python 解释器开销**：

- 即使所有热点 Cython 化，框架层仍有开销
- 未来可考虑子解释器（PEP 684）

**共享内存开销**：

- 跨进程协调有固定开销
- 单进程场景下可关闭

## 10. 调优建议

### 10.1 服务器调优

**内存相关**：

    # Buffer Pool 设为物理内存的 60%
    buffer_pool_size = 物理内存(GB) * 1024 * 1024 * 0.6 / 4096

    # 例：32 GB 内存
    buffer_pool_size = 5033164

**并发相关**：

    # Worker 数 = CPU 核数
    workers = 8

    # 单查询并行度 = CPU 核数
    parallel_workers = 8

    # 最大连接数
    max_connections = 500

**存储相关**：

    # 页大小
    page_size = 4096

    # 数据目录使用 NVMe SSD
    data_dir = /mnt/nvme/lightdb

**日志相关**：

    # 慢查询阈值
    slow_query_threshold = 0.5

    # 日志级别（生产环境用 INFO）
    log_level = INFO

### 10.2 应用侧调优

**连接池**：

- 每应用实例 5-20 连接
- 连接空闲超时 300 秒
- 心跳检测开启

**查询优化**：

- 避免 `SELECT *`
- 明确列名
- WHERE 走索引
- 避免 `LIKE '%xxx'`
- 加 LIMIT 保护

**批量操作**：

- 批量插入用 `INSERT INTO t VALUES (...), (...), ...`
- 批量大小 500-2000 行
- 避免单行提交

**事务控制**：

- 事务尽量短（< 1 秒）
- 避免大事务（> 10000 行）
- 无必要时关闭事务
