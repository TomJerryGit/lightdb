## 7. 性能优化技术

### 7.1 行格式优化

**v2.0（JSON）**：

    json.dumps(values).encode('utf-8')
    # 每行约 200 字节
    # 编解码耗时：编码 15ms/1000 行，解码 18ms/1000 行

**v3.0（二进制）**：

    [null_bitmap] [len1 data1] [len2 data2] ...
    # 每行约 70 字节
    # 编解码耗时：编码 5ms/1000 行，解码 4ms/1000 行

**效果**：

| 指标 | JSON  | Binary | 提升    |
|------|:-----:|:------:|:-------:|
| 编码 | 15ms  | 5ms    | 3.0x    |
| 解码 | 18ms  | 4ms    | 4.1x    |
| 大小 | 200B  | 70B    | 2.9x    |

### 7.2 批处理

**v2.0（逐行）**：

    for row in rows:
        process(row)

**v3.0（批处理 1024 行）**：

    for batch in chunks(rows, 1024):
        process_batch(batch)

**效果**：

- 减少 Python 函数调用次数
- 提升 1.37x

### 7.3 向量化执行

**v2.0（Python 循环）**：

    result = []
    for v in values:
        if v > 100:
            result.append(v)

**v3.0（NumPy）**：

    import numpy as np
    arr = np.array(values)
    result = arr[arr > 100]

**效果**：

- 10000 行过滤：Python 15.3ms，NumPy 5.8ms
- 提升 3.15x

### 7.4 计划缓存

**v2.0（每次解析）**：

    def execute(sql):
        ast = parser.parse(sql)     # 每次解析
        plan = optimizer.optimize(ast)
        return executor.run(plan)

**v3.0（缓存 AST + 计划）**：

    cache = PlanCache()

    def execute(sql):
        ast = cache.get_parsed(sql)
        if ast is None:
            ast = parser.parse(sql)
            cache.put_parsed(sql, ast)
        plan = cache.get_plan(sql)
        if plan is None:
            plan = optimizer.optimize(ast)
            cache.put_plan(sql, plan)
        return executor.run(plan)

**效果**：

- 相同 SQL 复用计划
- 减少 5-10% 的 CPU 消耗

### 7.5 读写分离

**v2.0（互斥锁）**：

    def scan(self):
        with self.mutex:        # 读写都加锁
            return self._do_scan()

**v3.0（读写锁）**：

    def scan(self):
        with self.rwlock.read():   # 多读不阻塞
            return self._do_scan()

**效果**：

- 读并发提升 50%
- 写操作仍独占

### 7.6 自适应页预读

**原理**：检测顺序访问模式，提前加载后续页。

    class AdaptivePrefetcher:
        def record(self, page_id):
            if self.last_page is not None and page_id == self.last_page + 1:
                self.seq_score += 1
            else:
                self.seq_score = max(0, self.seq_score - 2)
            self.last_page = page_id

        def prefetch_count(self):
            if self.seq_score >= 8:
                return 16
            elif self.seq_score >= 5:
                return 8
            elif self.seq_score >= 2:
                return 4
            return 0

**效果**：顺序扫描场景提升 20%。

- 纯 Python 实现

- 建议：Cython 化

**页操作（15%）**：

- 字节读写
- 校验和计算
- 建议：Cython 化

**网络层（8%）**：

- Python socket
- 协议打包/解包
- 建议：Cython 化

| Cython 页操作 | 5x       | page_pyx.pyx    |

### 8.4 GIL 影响量化

### 10.1 服务器调优

**内存相关**：

    # Buffer Pool 设为物理内存的 40%
    # v3.0 是单进程，预留 60% 给系统和 Python 运行时
    buffer_pool_size = 物理内存(GB) * 1024 * 1024 * 0.4 / 4096

    # 例：16 GB 内存
    buffer_pool_size = 1677721

**并发相关**：

    # v3.0 单进程，workers 固定为 1
    workers = 1

    # 单查询并行度
    parallel_workers = 2

    # 最大连接数（单进程不宜超过 500）
    max_connections = 200

**存储相关**：

    # 页大小
    page_size = 4096

    # 数据目录使用 SSD
    data_dir = /mnt/ssd/lightdb

**日志相关**：

    # 慢查询阈值
    slow_query_threshold = 0.5

    # 日志级别
    log_level = INFO

### 10.2 应用侧调优

**连接池**：

- 每应用实例 3-10 连接
- 连接空闲超时 300 秒
- v3.0 单进程，会话是稳定的

**查询优化**：

- 避免 `SELECT *`
- 明确列名
- WHERE 走索引
- 避免 `LIKE '%xxx'`
- 加 LIMIT 保护

**批量操作**：

- 批量插入用 `INSERT INTO t VALUES (...), (...), ...`
- 批量大小 500-1000 行
- 避免单行提交

**事务控制**：

- 事务尽量短（< 1 秒）
- 避免大事务（> 10000 行）

### 10.4 v3.0 特有的优化

由于 v3.0 是单进程（受 GIL 限制），提升性能的手段有限：

1. **加索引**：最有效
2. **增大 Buffer Pool**：减少磁盘 IO
3. **优化 SQL**：避免全表扫描
4. **提高单核性能**：换更好的 CPU
5. **启用计划缓存**：减少解析开销
6. **利用批处理**：一次操作多行

### 10.5 何时需要升级到 v4.0

**判断标准**：

| 场景                          | 建议          |
|-------------------------------|---------------|
| 单核 QPS 已足够（< 5,000）    | 保持 v3.0     |
| 多核利用率 < 20%              | 升级 v4.0     |
| 需要 OLAP 能力                | 升级 v4.0     |
| 需要高并发（> 10,000 QPS）    | 升级 v4.0     |
| 需要列存                      | 升级 v4.0     |

**v4.0 相比 v3.0**：

- 单线程：+85%
- 8 核并发：+1022%
- OLAP：新增
- 综合：MySQL 5.7 的 80% -> 125%
